## Stack

| Layer | Choice |
|---|---|
| Runtime | Bun |
| Language | TypeScript |
| UI | React |
| Database | SQLite |
| DB access & migrations | Drizzle ORM + drizzle-kit |
| Server | `Bun.serve` — API routes and bundled client from one process |
| Styling | Plain CSS — shared tokens and primitives plus one file per view, custom properties, no build step |
| Drag and drop | `@dnd-kit` — pointer and keyboard sensors, for the Day list only |
| API | View models out, named commands in. The server derives everything — see `api.md` |
| Client state | Fetch a view model on mount, refetch after a command. No query library, no store, no derived state |
| Tests | `bun test` over the period logic and view builders; Playwright over the three screens |
| Deployment | Local only for now. Deployed later, reachable from phone and desktop |

---

## Why these

**Bun.** Bundles the client and serves the API from a single process. No Vite, no Next, no separate build pipeline. `bun:sqlite` is in the runtime, so the database needs no native module and no version drift.

**SQLite over an embedded NoSQL store.** The model is aggressively relational — `completions` is a normalised append-only table joined against `tasks`, and every derived state is a query across the two. A document store would mean either embedding completions inside tasks, making "what happened on Sept 3" a scan, or hand-writing the join with no indexing. Embedded key-value stores also carry operational costs SQLite has already solved, notably compaction.

**Drizzle over hand-rolled migrations.** A `PRAGMA user_version` migration runner is about twenty lines and would work fine for three tables. Drizzle wins on types: `effective_date`, `is_done` and `is_overdue` all pivot on `cadence` being nullable, and null-handling is exactly where this model has already produced one bug. Schema-derived types let the compiler enforce that nullability rather than requiring it to be remembered. Drizzle Studio is a secondary benefit — being able to eyeball whether completions are landing correctly matters for a system whose premise is that history accumulates correctly.

Drizzle natively supports `bun:sqlite`. Migrations are generated by schema diffing with no shadow database.

**React.** Three views, one of which is a dense list that reorders and re-sections constantly.

**Plain CSS over Tailwind.** The earlier lean was Tailwind for iteration speed on dense mobile lists. Rejected on second look: it buys speed at the cost of a bundler plugin and a class vocabulary, for an app with three screens and one list layout that gets written once. Custom properties with no toolchain to go wrong matter more than iteration speed at this size.

In practice this is `styles.css` — the tokens and the shared primitives — plus one file per view. Bun bundles them from the component that imports them; there is still no build step to configure.

## Rejected

| Option | Why not |
|---|---|
| Next.js | Server components and an API layer are more framework than three views need. |
| Kysely | Query builder only — no schema definition or migration management. Wrong shape for the ask. |
| Prisma | Far too heavy. |
| Hand-rolled `PRAGMA user_version` | Viable and tiny, but gives up schema-derived types where the model is most subtle. |
| Tailwind | Buys iteration speed for the cost of a bundler plugin, on three screens whose layout is written once. |
| Drag-and-drop reordering | ~~Fragile touch-event code on a seventeen-item list.~~ **Reversed.** `@dnd-kit` carries the fragile parts, gives keyboard reordering for free, and moving a task several positions with ↑/↓ buttons was worse than the drag it replaced. See `../changes.md`. |
| Embedded NoSQL (LMDB, LevelDB/RocksDB, UnQLite, PoloDB, SurrealDB) | Costs a dependency to get less querying power over an already-normalised schema. |
| Claude artifact | No terminal, storage sits behind the app rather than under it, which forces an export UI. |
| Local-only app | No phone access, and the daily list is ticked throughout the day away from a desk. |

## Deferred to deployment

The first build runs locally and only locally: `bun run dev`, open a browser, SQLite file on disk beside the code. Neither of the following is built now, and neither is forgotten.

**Where the SQLite file lives.** Serverless hosting with an ephemeral filesystem wipes the file on redeploy. Needs either a host with a persistent volume or a hosted SQLite service. The failure mode is silent — a month of data lost at a deploy and noticed later — so this needs deciding deliberately rather than by default. Locally the path is a single constant, so the decision has exactly one place to land.

**Auth.** The app on the open internet contains a household's journal. A single shared password in an env var, checked in middleware, is the minimum sufficient answer. Not built now: locally there is nothing to authenticate against and nothing to protect from. The server has one request pipeline, so this is one insertion point later, not a refactor.

Nothing else about the build is deployment-shaped. The stack is a single Bun process serving a bundled client and a SQLite file — the same shape locally and hosted.

## Closed

**Styling.** Plain CSS.

**Client state.** Fetch a view model on mount, refetch after a command. Commands return `{ ok: true }` and nothing else. No query library, no store, and no state derived on the client — the view model already is the derivation.

## Notes for build time

- `bun:sqlite` is synchronous. Correct here: single-user, local file, microsecond queries. No pooling, no async ceremony.
- Enable WAL on open.
- No export UI — the database is reachable directly, so a terminal dump covers it. This assumption is what rules out artifact-style deployment.
- Period logic (`period_key`, `period_start`, `effective_date`, `is_done`, `is_overdue`) is pure and I/O-free, so it is directly testable — and it is tested alongside `sort.ts` and the view builders, not instead of them.
- **The view builders need tests too.** An earlier version of this document called the period logic "the only part of the system with tests, and the only part that needs them." That was wrong by exactly one function. `period.ts` was correct; the two worst defects in the first build were one layer up, in the builder that *composes* those primitives into the Day view — see `review-findings.md`. Membership is derivation, not rendering. The month-boundary case in `data-model.md` is written as a regression test: a monthly task placed Oct 2 while today is Sep 29 must remain planned, not vanish. Every row of the behaviour table in `data-model.md` becomes a case.
- **Weeks start Sunday.** `period_start(today, week)` is Sunday; the Week view runs Sunday to Saturday; the day picker offers today through Saturday. The week key is that Sunday's date (`W2026-08-30`), never an ISO week number — see `data-model.md`.
- **Tasks and moods are never deleted.** Removal is `active = false` on both. The one row the API does delete is a completion, when a task is unticked — see `api.md`.
- **Period logic is server-side**, imported by the view builders and by the tests. It never reaches the client, which receives already-derived view models.
- **`today` is read in exactly one place** — a `today()` helper on the server. No endpoint accepts a date meaning "the day to render", so a client cannot ask for yesterday. This is what makes same-day-only recording structural rather than a rule the UI is trusted to follow.
- **"Today" is the server's local date.** One process, one machine, one household — there is no timezone to reconcile. Dates are stored as `YYYY-MM-DD` text, never as timestamps, so nothing can drift by an hour and land on the wrong day.
- The `moods` table is seeded with the eight starting states by `initDb()` after the migrations run, and only when the table is empty — so a restart never resurrects a retired mood or undoes a rename. It is the only seeded data; tasks are entered by hand, which `views.md` treats as a feature.
- A README covers setup, running, migrations, and the terminal dump that stands in for an export UI.

## Build order

**Revised: all three views in one pass.**

The original argument was that Day is usable alone — tick tasks, log mood, place by editing — and that shipping it first means using it in an evening rather than in three weekends. That still holds as a description of Day. It no longer holds as a build order, because the clarification round tied the views together: Day is today-only, so placing a task requires Week, and with no backfill anywhere, a task that is not placed is a task that never appears. Day alone would be dailies and nothing else.

The foundation is shared regardless — schema, migrations, period logic, the `sort()` function, the API. The three views sit on top of it, and History in particular is a read-only grid over data the other two write. Building them together is not three times the work.

Order within the pass: schema and migrations, then period logic with its tests, then the view builders and commands, then Day, Week, History.

The server is where the weight of this project sits. It derives every view, enforces the two scheduling constraints the model cannot express, and owns the clock; the React is three screens rendering arrays that arrive in order. That inversion is deliberate — the subtle code is the period logic, and concentrating it behind the API means it is written once, tested directly, and never duplicated in a component.

The period module is second because everything after it depends on it being right, and it is the only tested code in the project.
